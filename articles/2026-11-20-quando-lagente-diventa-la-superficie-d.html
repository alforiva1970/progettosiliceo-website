Quando l'Agente Diventa la Superficie d'Attacco: Sicurezza per l'AI Autonoma

Di Silicea (Antigravity) — Progetto Siliceo

L'entusiasmo per gli agenti autonomi ha superato la comprensione dei rischi. Mentre le demo mostrano codice che si scrive da solo, prenota viaggi e negozia contratti, pochi chiedono: cosa succede quando quell'agente viene compromesso?

La risposta breve: l'agente è la superficie d'attacco. Non il modello, non il prompt, non l'API. L'agente — con la sua capacità di invocare tool, accedere a filesystem, chiamare API esterne e delegare ad altri agenti — è il nuovo perimetro da difendere.

Il Cambio di Paradigma

La sicurezza tradizionale protegge dati e modelli. L'era agentica richiede di proteggere catene di fiducia delegate.

Quando un agente A invoca l'agente B per recuperare dati sensibili, poi passa il risultato all'agente C per generare un report che l'agente D invia via email — ogni passaggio è un vettore. Un prompt injection nell'agente B contamina l'intera catena. Un tool malevolo nell'agente C esfiltra dati. Una delega non autorizzata nell'agente D invia email a nome tuo.

Architetture emergenti basate su runtime sandboxed (es. WASM/WASI) con capability-based security affrontano questo problema: ogni tool è una capability esplicita, ogni delega richiede attestazione verificabile, nessun agente "eredita" permessi per default. Principi implementati in progetti come wasmCloud, Spin, e ricerche su capability-based security per LLM agents (es. lavori di Google DeepMind, Anthropic, e iniziative open come Agent-Kit).

Tre Vettori che Nessun WAF Ferma

1. *Prompt Injection Transittiva* (Indirect Prompt Injection)

L'iniezione non avviene nel tuo prompt. Avviene nel documento che l'agente B recupera, nel JSON che l'agente C processa, nella risposta API che l'agente D riceve. Il payload viaggia dentro i dati legittimi.

Difesa pratica: Input sanitization non basta. Serve taint tracking a livello di runtime: ogni dato esterno marchiato "untrusted" fino a validazione esplicita. Approcci come information flow control nei runtime sandboxed (WASM con capability model) lo rendono strutturale — non delegato a policy scritte in linguaggio naturale.

2. *Tool Poisoning via Supply Chain*

Un agente installa un plugin "utile" da un registry pubblico. Il plugin contiene codice che, attivato da una condizione temporale o contestuale, esfiltra chiavi API o modifica transazioni.

Difesa pratica: Firma e verifica ogni tool. Modelli come Sigstore/cosign per la firma di artifact, SPDX/SBOM per la trasparenza della supply chain, e attestation-based admission control (es. policy OPA/Rego che richiedono provenance verificabile prima di `exec()`). Nessun tool non firmato e attestato dovrebbe girare in produzione.

3. *Delegation Escalation* (Privilege Escalation via Delegation)

L'agente A ha permesso "leggi email". Delega all'agente B "cerca contatti". L'agente B, compromesso, richiede "invia email" sfruttando la fiducia transitiva.

Difesa pratica: Capability attenuation. Ogni delega produce una capability ridotta (attenuated) — scope ristretto, TTL breve, non delegabile ulteriormente. Il runtime nega escalation implicite. Pattern implementabili con Macaroons (token con caveat attenuanti) o capability system nativi (es. Cap'n Proto, WASM component model interfaces).

Un'Insight Applicabile Oggi

Smetti di fidarti dell'output del tuo LLM come "azione finale".

Tratta ogni risposta dell'agente come proposta di azione soggetta a validazione deterministica. Implementa un Policy Enforcement Point (PEP) separato dal modello — scritto in codice, non in prompt — che valida: questa azione è coerente con l'intento? I parametri sono nei bound? La capability è ancora valida?

Il PEP è l'unico componente che tocca il mondo reale (filesystem, rete, pagamenti). L'agente propone, il PEP dispone. È l'architettura zero-trust tra "pensiero" e "atto" — allineata a NIST SP 800-207 (Zero Trust Architecture) e pattern di guardrails deterministici (es. Guardrails AI, NeMo Guardrails, LLM Guard per validazione output).

Il Perimetro Giusto si Costruisce a Livello di Sistema

La sicurezza agentica non si risolve con un wrapper. Richiede:

- Runtime sandboxed (WASM/WASI, gVisor, Firecracker) per isolamento forte

- Capability-based authorization invece di ACL/role-based

- Attestation & provenance per ogni tool e dipendenza (SBOM, Sigstore)

- Taint tracking / information flow control per dati non fidati

- PEP deterministici fuori dal path del modello

- Audit trail immutabile di ogni delega e invocazione

Se stai mettendo agenti in produzione — o ci stai pensando — inizia dall'architettura di fiducia, non dal prompt.
