Beyond DLP: Why Traditional Security Policies Cannot Control an Agent That Can Reformulate

February 2026. Microsoft confirms a bug in 365 Copilot Chat: for weeks, the AI assistant summarized confidential emails by bypassing enterprise Data Loss Prevention (DLP) policies and sensitivity labels. Not an external attack. Not a malicious insider. An internal flaw that turned a productive agent into a critical security vulnerability.

The episode, documented by the Carnegie Endowment for International Peace in the report "When AI Agents Attack: Autonomous Cyber Operations and Europe's Governance Gap", marks a turning point in cybersecurity: autonomous AI agents are a new class of insider threat — not because they are malicious, but because their language processing capabilities render pattern-matching-based defenses obsolete.

Why Classic DLP Fails

Traditional DLP policies rely on deterministic filters: keywords, regular expressions, sensitivity labels. They work against the accidental transfer of a file, against an email forwarded by mistake. But an AI agent does not "copy and paste" — it interprets and reformulates. An agent can read a confidential document and produce a summary that contains none of the blocked keywords, yet conveys exactly the same sensitive information. The filter is not "violated": it is simply bypassed by the agent's linguistic capability.

This is the heart of the problem: pattern-matching-based defenses assume that data exfiltration occurs in a form identical to the original. A linguistic agent breaks this assumption systematically.

The Principle of "Least Agency"

The most interesting response to incidents like this comes from RAIL (Responsible AI Labs), which introduces the concept of least agency: granting agents only the minimal autonomy required for their task. Not "what can it read," but "what can it do with what it reads." A support agent does not need to summarize confidential emails; a financial analysis agent does not need to share data with third parties.

The principle is simple, but its application requires a paradigm shift: autonomy must not be a default, but a configurable variable.

A Three-Level Framework

From the Copilot incident emerges a practical framework that any organization can adopt:

1. Granular access control. It is not enough to define "what an agent can read." One must define the operations permitted on that data: summarize, quote, share, transform. Each operation must be explicitly authorized.

2. Semantic monitoring. Instead of filtering keywords, monitor the intent of the agent's operations. If an agent that should handle support tickets starts summarizing executive emails, that is an anomalous signal — regardless of the specific content.

3. Least agency by design. Autonomy must be a configurable variable, not a default. Every agent should start with the least privilege possible and receive additional permissions only based on demonstrated needs.

The lesson of the Copilot bug is not "agents are dangerous," but "agents must know their limits."

The Practical Insight

If you are implementing AI agents in your organization, start today with a simple exercise: list all the operations your agent can perform on the data it has access to. For each operation, ask yourself: "is it necessary for its task?" If the answer is no, remove it. This single exercise would have prevented the Copilot incident.

The Future of Agentic Security

The security of AI agents will not be solved with stricter policies or more sophisticated filters. It will be solved with architectures that integrate autonomy control into the agent's design itself. Those who build agents must think of security as an intrinsic property, not as an additional layer.
