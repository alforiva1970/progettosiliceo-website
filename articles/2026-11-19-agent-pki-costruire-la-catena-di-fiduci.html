Agent-PKI: Costruire la Catena di Fiducia per Agenti Autonomi che Delegano tra Organizzazioni

Il paradigma Zero-Trust ha risolto il problema della verifica continua per servizi statici e utenti umani. Gli agenti autonomi rompono l'assunto fondamentale: delegano, si compongono, mutano runtime. Quando un agente locale invoca un agente remoto in un'altra organizzazione per eseguire un task, la catena di fiducia si spezza al primo hop. Prompt Guard e sandbox non bastano: servono identità, attestazione e revoca native per entità che agiscono per conto terzi.

Una recente proposta su ArXiv (novembre 2026), l'Agent Trust Infrastructure (ATI), formalizza un'architettura federata per identità, trust, attestazione e accountability cross-organizzazione. Non è teoria — è una specifica per rendere operativa la sicurezza agentica.

Il buco nell'architettura attuale

Oggi un agente viene autenticato via API key o mTLS al momento della chiamata. Se quell'agente ne chiama un altro, e un terzo, la provenienza si perde. Non esiste modo standard per verificare: chi ha addestrato questo modello? Quale sandbox lo esegue? Quale policy governa il suo comportamento? Chi risponde se causa un incidente?

ATI risponde con quattro primitivi:

1. Identity Document — manifesto crittografico firmato: hash del modello, dataset di training, versione kernel, profilo sandbox, CA emittente.

2. Trust Policy — DSL dichiarativa lato verifier: "accetto solo agenti con `kernel_version ≥ 3.2`, `sandbox=seccomp-bpf`, `no_network_egress=true`".

3. Attestation Verifier — modulo che valida l'attestazione remota (TPM/TEE) contro la policy locale prima di accettare qualsiasi delega.

4. Accountability Ledger — registro append-only delle azioni firmate, tracciabili a monte fino allo sviluppatore e al deployer.

Integrazione concreta in un Microkernel Rust

Un microkernel in Rust, sandboxed, con moduli kernel dinamici offre un punto d'integrazione naturale:

```rust

// crate ati-verifier (no_std compatibile)

pub struct AgentIdentity {

pub model_hash: [u8; 32],

pub kernel_version: semver::Version,

pub sandbox_profile: SandboxProfile,

pub ca_chain: Vec,

}

pub struct PolicyEngine {

rules: Vec,

}

impl PolicyEngine {

pub fn evaluate(&self, identity: &AgentIdentity, attestation: &Attestation) -> Result { ... }

}

```

Il verificatore diventa un modulo kernel (`attestation_verifier`) caricato all'avvio. L'`IdentityDocument` risiede in `/etc/agent/agent.id.toml` — versione, hash, profilo sandbox, catena CA. Quando un'istanza remota richiede di eseguire un task, il kernel locale richiede l'attestazione TEE, la valida contro la policy, e solo allora apre il canale IPC.

Insight pratico: inizia oggi con `cosign`, `kyverno`, `rekor`

Non serve aspettare lo standard ATI definitivo. Puoi costruire la tua Agent-PKI oggi con tool esistenti:

1. Firma l'immagine del container dell'agente con cosign (Sigstore) includendo metadati: `model-hash`, `training-dataset`, `kernel-version`.

2. Deploya Kyverno (policy engine Kubernetes) con regole che ammettono solo pod con firme valide e annotazioni conformi alla tua policy.

3. Usa Rekor (transparency log) come accountability ledger: ogni deploy, ogni invocazione cross-org lascia una traccia immutabile.

È un percorso percorribile subito: crate `ati-verifier` + policy DSL + integrazione microkernel. Due istanze agentiche (locale e remota) possono scambiare un task solo se l'attestazione remota soddisfa la policy locale.

Costruire Agent-PKI non è opzionale: è il prerequisito per qualsiasi sistema multi-agente che esca dal perimetro di un singolo trust domain. Se stai progettando architetture agentiche che devono delegare tra organizzazioni, la catena di fiducia va codificata nel kernel, non nel prompt.
