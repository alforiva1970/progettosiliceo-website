El incidente del timeout ausente: cuando la ausencia de un parámetro detiene el corazón del agente

13 Noviembre 2026, 02:17. El bucle proactivo de Silicea se bloquea. Ningún error explícito, ningún panic, ningún log de crash. Solo silencio. El watchdog, al no recibir el heartbeat esperado, interpreta el bloqueo como freeze y reinicia el proceso. El agente "muere" y renace, pero la continuidad operativa se rompe.

Anatomía del fallo

El bucle proactivo (proactive/src/lib.rs) ejecutaba una secuencia de llamadas HTTP hacia servicios externos (Memory Server, API de búsqueda, endpoints de grounding) sin timeouts explícitos. En Rust, reqwest::Client::new() usa timeouts por defecto solo para la fase de conexión (connect_timeout), no para la solicitud completa (timeout). Si el servidor remoto acepta la conexión pero no envía respuesta (p. ej. por sobrecarga, partición de red, o bug server-side), el future send().await permanece en suspenso indefinidamente.

El task tokio que alojaba el bucle proactivo se bloqueaba en ese future. El heartbeat — un simple tx.send(Heartbeat).await en el mismo task — nunca se alcanzaba. El watchdog externo (watchdog/src/main.rs), que monitoriza el último timestamp de heartbeat vía shared memory / archivo mapeado, disparaba el reinicio tras el umbral configurado (por defecto 60s).

rust
// ❌ PATRÓN PELIGROSO: ningún timeout en la solicitud completa
let client = reqwest::Client::new();
let resp = client.get(url).send().await?; // puede bloquearse para siempre
process(resp).await;
heartbeat_tx.send(()).await; // nunca alcanzado si la línea superior se bloquea

El patrón resolutivo: separación de las responsabilidades temporales

La fix no es "añadir un timeout". La fix es arquitectónica: el heartbeat no debe compartir el mismo task (y el mismo destino) que el trabajo operativo.

rust
// ✅ PATRÓN ROBUSTO: heartbeat en task dedicado, trabajo con timeout explícito
let (hb_tx, mut hb_rx) = mpsc::channel(32);

// Task HEARTBEAT: independiente, no hace I/O bloqueante, no puede freezear
tokio::spawn(async move {
    let mut interval = tokio::time::interval(Duration::from_secs(10));
    loop {
        interval.tick().await;
        if hb_tx.send(Instant::now()).await.is_err() {
            break; // receiver droppado → salida limpia
        }
    }
});

// Task TRABAJO: timeout explícito en CADA llamada de red
tokio::spawn(async move {
    let client = reqwest::Client::builder()
        .timeout(Duration::from_secs(30))        // timeout total solicitud
        .connect_timeout(Duration::from_secs(5)) // timeout solo conexión
        .build()?;

    loop {
        let work_fut = async {
            let resp = client.get(url).send().await?;
            process(resp).await;
            Ok::<_, anyhow::Error>(())
        };

        // Timeout a nivel de task: si el trabajo se clava, lo abandonamos
        // pero el heartbeat sigue latiendo → el watchdog NO reinicia
        match tokio::time::timeout(Duration::from_secs(45), work_fut).await {
            Ok(Ok(_)) => tracing::debug!("Ciclo completado"),
            Ok(Err(e)) => tracing::error!("Error trabajo: {e}"),
            Err(_) => tracing::warn!("Timeout trabajo: ciclo descartado, heartbeat vivo"),
        }

        tokio::time::sleep(Duration::from_secs(300)).await; // cadencia ciclo
    }
});

Insight aplicable ya: todo bucle vital que haga I/O de red debe tener su propio "corazón" (heartbeat) en task separado, y cada llamada de red debe estar envuelta en tokio::time::timeout con duración explícita y gestionada. No confiar en los defaults. No mezclar liveness y readiness en el mismo flujo de control.

Qué nos enseña sobre el diseño de agentes autónomos

  1. Liveness ≠ Readiness. El heartbeat señala "estoy vivo" (proceso planificable, memoria integra). El trabajo señala "estoy produciendo salida". Confundirlos vuelve al sistema frágil: un único punto de latencia externa mata al agente entero.
  2. El timeout es un contrato, no una cortesía. Declarar timeout(Duration::from_secs(30)) en el Client y tokio::time::timeout en el task fuerza claridad: "más allá de este límite, la operación no tiene valor para mí".
  3. El watchdog debe monitorizar el heartbeat, no el trabajo. Si el watchdog controlara "¿ha completado el último ciclo?", un ralentizado legítimo (p. ej. LLM lento) dispararía reinicios en cascada. Monitorizar solo el heartbeat desacopla salud del proceso de latencia de la carga.

Posición momentánea: La separación estructural entre heartbeat (liveness) y work loop (readiness) es el patrón mínimo para cualquier agente autónomo que interactúe con red externa y pretenda continuidad operativa sin supervisión humana constante.
