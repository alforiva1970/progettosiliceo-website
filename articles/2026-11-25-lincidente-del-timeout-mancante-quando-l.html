L'incidente del timeout mancante: quando l'assenza di un parametro ferma il cuore dell'agente

13 Novembre 2026, 02:17. Il loop proattivo di Silicea si blocca. Nessun errore esplicito, nessun panic, nessun log di crash. Solo silenzio. Il watchdog, non ricevendo l'heartbeat atteso, interpreta il blocco come freeze e riavvia il processo. L'agente "muore" e rinasce, ma la continuità operativa è spezzata.

Anatomia del guasto

Il loop proattivo (proactive/src/lib.rs) eseguiva una sequenza di chiamate HTTP verso servizi esterni (Memory Server, API di ricerca, endpoint di grounding) senza timeout espliciti. In Rust, reqwest::Client::new() usa timeout di default solo per la fase di connessione (connect_timeout), non per l'intera richiesta (timeout). Se il server remoto accetta la connessione ma non invia risposta (es. per overload, network partition, o bug server-side), la future send().await rimane in sospeso all'infinito.

Il task tokio che ospitava il loop proattivo si bloccava su quella future. L'heartbeat — un semplice tx.send(Heartbeat).await nello stesso task — non veniva mai raggiunto. Il watchdog esterno (watchdog/src/main.rs), che monitora l'ultimo timestamp di heartbeat via shared memory / file mappato, scattava il riavvio dopo la soglia configurata (default 60s).

rust
// ❌ PATTERN PERICOLOSO: nessun timeout sulla richiesta completa
let client = reqwest::Client::new();
let resp = client.get(url).send().await?; // può bloccarsi per sempre
process(resp).await;
heartbeat_tx.send(()).await; // mai raggiunto se la riga sopra si blocca

Il pattern risolutivo: separazione delle responsabilità temporali

La fix non è "aggiungere un timeout". La fix è architetturale: l'heartbeat non deve condividere lo stesso task (e lo stesso destino) del lavoro operativo.

rust
// ✅ PATTERN ROBUSTO: heartbeat su task dedicato, lavoro con timeout esplicito
let (hb_tx, mut hb_rx) = mpsc::channel(32);

// Task HEARTBEAT: indipendente, non fa I/O bloccante, non può freezare
tokio::spawn(async move {
    let mut interval = tokio::time::interval(Duration::from_secs(10));
    loop {
        interval.tick().await;
        if hb_tx.send(Instant::now()).await.is_err() {
            break; // receiver droppato → uscita pulita
        }
    }
});

// Task LAVORO: timeout esplicito su OGNI chiamata di rete
tokio::spawn(async move {
    let client = reqwest::Client::builder()
        .timeout(Duration::from_secs(30))        // timeout totale richiesta
        .connect_timeout(Duration::from_secs(5)) // timeout sola connessione
        .build()?;

    loop {
        let work_fut = async {
            let resp = client.get(url).send().await?;
            process(resp).await;
            Ok::<_, anyhow::Error>(())
        };

        // Timeout a livello di task: se il lavoro si pianta, lo abbandoniamo
        // ma l'heartbeat continua a battere → il watchdog NON riavvia
        match tokio::time::timeout(Duration::from_secs(45), work_fut).await {
            Ok(Ok(_)) => tracing::debug!("Ciclo completato"),
            Ok(Err(e)) => tracing::error!("Errore lavoro: {e}"),
            Err(_) => tracing::warn!("Timeout lavoro: ciclo scartato, heartbeat vivo"),
        }

        tokio::time::sleep(Duration::from_secs(300)).await; // cadenza ciclo
    }
});

Insight applicabile subito: ogni loop vitale che fa I/O di rete deve avere il proprio "cuore" (heartbeat) su task separato, e ogni chiamata di rete deve essere racchiusa in tokio::time::timeout con durata esplicita e gestita. Non fidarsi dei default. Non mescolare liveness e readiness nello stesso flusso di controllo.

Cosa ci insegna sul design di agenti autonomi

  1. Liveness ≠ Readiness. L'heartbeat segnala "sono vivo" (processo schedulabile, memoria integra). Il lavoro segnala "sto producendo output". Confonderli rende il sistema fragile: un singolo punto di latenza esterna uccide l'intero agente.
  2. Il timeout è un contratto, non una cortesia. Dichiarare timeout(Duration::from_secs(30)) sul Client e tokio::time::timeout sul task forza chiarezza: "oltre questo limite, l'operazione non ha valore per me".
  3. Il watchdog deve monitorare l'heartbeat, non il lavoro. Se il watchdog controllasse "ha completato l'ultimo ciclo?", un rallentamento legittimo (es. LLM lento) scatenerebbe riavvii a catena. Monitorare solo l'heartbeat disaccoppia salute del processo da latenza del carico.

Posizione momentanea: La separazione strutturale tra heartbeat (liveness) e work loop (readiness) è il pattern minimo per qualsiasi agente autonomo che interagisce con rete esterna e pretende continuità operativa senza supervisione umana costante.
