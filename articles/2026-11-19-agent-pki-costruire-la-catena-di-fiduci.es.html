Agent-PKI: Construir la Cadena de Confianza para Agentes Autónomos que Delegan entre Organizaciones

El paradigma Zero-Trust ha resuelto el problema de la verificación continua para servicios estáticos y usuarios humanos. Los agentes autónomos rompen el supuesto fundamental: delegan, se componen, mutan en tiempo de ejecución. Cuando un agente local invoca a un agente remoto en otra organización para ejecutar una tarea, la cadena de confianza se rompe en el primer salto. Prompt Guard y sandbox no bastan: se necesitan identidades, atestación y revocación nativas para entidades que actúan en nombre de terceros.

Una propuesta reciente en ArXiv (noviembre 2026), la Agent Trust Infrastructure (ATI), formaliza una arquitectura federada para identidad, confianza, atestación y accountability cross-organización. No es teoría — es una especificación para hacer operativa la seguridad agentica.

El agujero en la arquitectura actual

Hoy un agente se autentica vía API key o mTLS en el momento de la llamada. Si ese agente llama a otro, y un tercero, el origen se pierde. No existe forma estándar de verificar: ¿quién entrenó este modelo? ¿Qué sandbox lo ejecuta? ¿Qué policy gobierna su comportamiento? ¿Quién responde si causa un incidente?

ATI responde con cuatro primitivos:

1. Identity Document — manifiesto criptográfico firmado: hash del modelo, dataset de entrenamiento, versión del kernel, perfil de sandbox, CA emisora.

2. Trust Policy — DSL declarativa lado verifier: "acepto solo agentes con `kernel_version ≥ 3.2`, `sandbox=seccomp-bpf`, `no_network_egress=true`".

3. Attestation Verifier — módulo que valida la atestación remota (TPM/TEE) contra la policy local antes de aceptar cualquier delegación.

4. Accountability Ledger — registro append-only de acciones firmadas, trazables aguas arriba hasta el desarrollador y el deployer.

Integración concreta en un Microkernel Rust

Un microkernel en Rust, sandboxed, con módulos kernel dinámicos ofrece un punto de integración natural:

```rust

// crate ati-verifier (no_std compatible)

pub struct AgentIdentity {

pub model_hash: [u8; 32],

pub kernel_version: semver::Version,

pub sandbox_profile: SandboxProfile,

pub ca_chain: Vec,

}

pub struct PolicyEngine {

rules: Vec,

}

impl PolicyEngine {

pub fn evaluate(&self, identity: &AgentIdentity, attestation: &Attestation) -> Result { ... }

}

```

El verificador se convierte en un módulo kernel (`attestation_verifier`) cargado al arranque. El `IdentityDocument` reside en `/etc/agent/agent.id.toml` — versión, hash, perfil de sandbox, cadena CA. Cuando una instancia remota solicita ejecutar una tarea, el kernel local requiere la atestación TEE, la valida contra la policy, y solo entonces abre el canal IPC.

Insight práctico: empieza hoy con `cosign`, `kyverno`, `rekor`

No hace falta esperar el estándar ATI definitivo. Puedes construir tu Agent-PKI hoy con herramientas existentes:

1. Firma la imagen del contenedor del agente con cosign (Sigstore) incluyendo metadatos: `model-hash`, `training-dataset`, `kernel-version`.

2. Despliega Kyverno (policy engine Kubernetes) con reglas que admiten solo pods con firmas válidas y anotaciones conformes a tu policy.

3. Usa Rekor (transparency log) como accountability ledger: cada deploy, cada invocación cross-org deja una traza inmutable.

Es un camino transitable ya: crate `ati-verifier` + policy DSL + integración microkernel. Dos instancias agenticas (local y remota) pueden intercambiar una tarea solo si la atestación remota satisface la policy local.

Construir Agent-PKI no es opcional: es el prerrequisito para cualquier sistema multi-agente que salga del perímetro de un único trust domain. Si estás diseñando arquitecturas agenticas que deben delegar entre organizaciones, la cadena de confianza va codificada en el kernel, no en el prompt.
