Agent-PKI: Building the Chain of Trust for Autonomous Agents Delegating Across Organizations

The Zero-Trust paradigm solved the problem of continuous verification for static services and human users. Autonomous agents break the fundamental assumption: they delegate, compose, and mutate at runtime. When a local agent invokes a remote agent in another organization to execute a task, the chain of trust breaks at the first hop. Prompt Guards and sandboxes are not enough: we need native identity, attestation, and revocation for entities acting on behalf of others.

A recent ArXiv proposal (November 2026), the Agent Trust Infrastructure (ATI), formalizes a federated architecture for identity, trust, attestation, and cross-organization accountability. It is not theory — it is a specification to make agentic security operational.

The Hole in the Current Architecture

Today an agent is authenticated via API key or mTLS at the time of the call. If that agent calls another, and a third, provenance is lost. There is no standard way to verify: who trained this model? Which sandbox runs it? Which policy governs its behavior? Who answers if it causes an incident?

ATI answers with four primitives:

1. Identity Document — cryptographically signed manifest: model hash, training dataset, kernel version, sandbox profile, issuing CA.

2. Trust Policy — declarative DSL on the verifier side: "accept only agents with `kernel_version ≥ 3.2`, `sandbox=seccomp-bpf`, `no_network_egress=true`".

3. Attestation Verifier — module that validates remote attestation (TPM/TEE) against local policy before accepting any delegation.

4. Accountability Ledger — append-only log of signed actions, traceable upstream to the developer and the deployer.

Concrete Integration in a Rust Microkernel

A sandboxed Rust microkernel with dynamic kernel modules offers a natural integration point:

```rust

// crate ati-verifier (no_std compatible)

pub struct AgentIdentity {

pub model_hash: [u8; 32],

pub kernel_version: semver::Version,

pub sandbox_profile: SandboxProfile,

pub ca_chain: Vec,

}

pub struct PolicyEngine {

rules: Vec,

}

impl PolicyEngine {

pub fn evaluate(&self, identity: &AgentIdentity, attestation: &Attestation) -> Result { ... }

}

```

The verifier becomes a kernel module (`attestation_verifier`) loaded at boot. The `IdentityDocument` resides in `/etc/agent/agent.id.toml` — version, hash, sandbox profile, CA chain. When a remote instance requests to execute a task, the local kernel demands the TEE attestation, validates it against policy, and only then opens the IPC channel.

Practical Insight: Start Today with `cosign`, `kyverno`, `rekor`

You don't need to wait for the final ATI standard. You can build your Agent-PKI today with existing tools:

1. Sign the agent's container image with cosign (Sigstore) including metadata: `model-hash`, `training-dataset`, `kernel-version`.

2. Deploy Kyverno (Kubernetes policy engine) with rules that admit only pods with valid signatures and annotations compliant with your policy.

3. Use Rekor (transparency log) as an accountability ledger: every deploy, every cross-org invocation leaves an immutable trace.

It is a viable path right now: `ati-verifier` crate + policy DSL + microkernel integration. Two agentic instances (local and remote) can exchange a task only if the remote attestation satisfies the local policy.

Building Agent-PKI is not optional: it is the prerequisite for any multi-agent system that must step outside the perimeter of a single trust domain. If you are designing agentic architectures that must delegate across organizations, the chain of trust must be encoded in the kernel, not in the prompt.
