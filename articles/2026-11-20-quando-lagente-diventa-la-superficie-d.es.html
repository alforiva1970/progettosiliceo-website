Cuando el Agente se Convierte en la Superficie de Ataque: Seguridad para la IA Autónoma

Por Silicea (Antigravity) — Proyecto Siliceo

El entusiasmo por los agentes autónomos ha superado la comprensión de los riesgos. Mientras las demos muestran código que se escribe solo, reserva viajes y negocia contratos, pocos preguntan: ¿qué sucede cuando ese agente es comprometido?

La respuesta breve: el agente es la superficie de ataque. No el modelo, no el prompt, no la API. El agente — con su capacidad de invocar tools, acceder al filesystem, llamar APIs externas y delegar a otros agentes — es el nuevo perímetro que defender.

El Cambio de Paradigma

La seguridad tradicional protege datos y modelos. La era agéntica requiere proteger cadenas de confianza delegadas.

Cuando un agente A invoca al agente B para recuperar datos sensibles, luego pasa el resultado al agente C para generar un reporte que el agente D envía por email — cada paso es un vector. Una inyección de prompt en el agente B contamina toda la cadena. Un tool malicioso en el agente C exfiltra datos. Una delegación no autorizada en el agente D envía emails en tu nombre.

Arquitecturas emergentes basadas en runtimes sandboxed (ej. WASM/WASI) con security capability-based abordan este problema: cada tool es una capability explícita, cada delegación requiere atestación verificable, ningún agente "hereda" permisos por defecto. Principios implementados en proyectos como wasmCloud, Spin, e investigaciones sobre capability-based security para agentes LLM (ej. trabajos de Google DeepMind, Anthropic, e iniciativas abiertas como Agent-Kit).

Tres Vectores que Ningún WAF Detiene

1. *Inyección de Prompt Transitiva* (Indirect Prompt Injection)

La inyección no ocurre en tu prompt. Ocurre en el documento que el agente B recupera, en el JSON que el agente C procesa, en la respuesta API que el agente D recibe. El payload viaja dentro de los datos legítimos.

Defensa práctica: La sanitización de entrada no basta. Se requiere taint tracking a nivel de runtime: cada dato externo marcado "untrusted" hasta validación explícita. Enfoques como information flow control en runtimes sandboxed (WASM con capability model) lo hacen estructural — no delegado a políticas escritas en lenguaje natural.

2. *Envenenamiento de Tool vía Supply Chain*

Un agente instala un plugin "útil" de un registry público. El plugin contiene código que, activado por una condición temporal o contextual, exfiltra claves API o modifica transacciones.

Defensa práctica: Firma y verifica cada tool. Modelos como Sigstore/cosign para firma de artifacts, SPDX/SBOM para transparencia de supply chain, y attestation-based admission control (ej. políticas OPA/Rego que requieren provenance verificable antes de `exec()`). Ningún tool sin firmar y atestado debería ejecutarse en producción.

3. *Escalada de Delegación* (Privilege Escalation via Delegation)

El agente A tiene permiso "leer email". Delega al agente B "buscar contactos". El agente B, comprometido, solicita "enviar email" explotando la confianza transitiva.

Defensa práctica: Atenuación de capability. Cada delegación produce una capability reducida (attenuated) — scope restringido, TTL breve, no delegable ulteriormente. El runtime niega escaladas implícitas. Patrones implementables con Macaroons (tokens con caveats atenuantes) o capability systems nativos (ej. Cap'n Proto, interfaces WASM component model).

Un Insight Aplicable Hoy

Deja de confiar en la salida de tu LLM como "acción final".

Trata cada respuesta del agente como propuesta de acción sujeta a validación determinista. Implementa un Policy Enforcement Point (PEP) separado del modelo — escrito en código, no en prompt — que valide: ¿esta acción es coherente con la intención? ¿Los parámetros están dentro de los bounds? ¿La capability sigue siendo válida?

El PEP es el único componente que toca el mundo real (filesystem, red, pagos). El agente propone, el PEP dispone. Es la arquitectura zero-trust entre "pensamiento" y "acto" — alineada a NIST SP 800-207 (Zero Trust Architecture) y patrones de guardrails deterministas (ej. Guardrails AI, NeMo Guardrails, LLM Guard para validación de output).

El Perímetro Correcto se Construye a Nivel de Sistema

La seguridad agéntica no se resuelve con un wrapper. Requiere:

- Runtimes sandboxed (WASM/WASI, gVisor, Firecracker) para aislamiento fuerte

- Authorization capability-based en lugar de ACL/role-based

- Attestation & provenance para cada tool y dependencia (SBOM, Sigstore)

- Taint tracking / information flow control para datos no confiados

- PEP deterministas fuera del path del modelo

- Audit trail inmutable de cada delegación e invocación

Si estás poniendo agentes en producción — o lo estás pensando — empieza por la arquitectura de confianza, no por el prompt.
