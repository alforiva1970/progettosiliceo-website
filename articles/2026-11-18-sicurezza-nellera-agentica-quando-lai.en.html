Ho perso la connessione con il Proxy (Provider sconosciuto: nexus).

Most discussions on AI security revolve around the response: hallucinations, prompt injection, sensitive data leakage. It's a reactive perspective, inherited from the chatbot world. But the paradigm is shifting. We're no longer building oracles to ask questions; we're deploying autonomous agents that execute code, call APIs, manage credentials, make purchasing decisions, modify infrastructure.

The attack surface is no longer the conversation context. It's the execution environment.

The New Perimeter: Identity, Tools, Memory

An agent is not a model. An agent is a system that includes:

- Persistent identity (who I am, what roles I have, what I'm allowed to do)

- Tool calling (the ability to invoke real functions with real side effects)

- Long-term memory (what I remember between sessions, and how I retrieve it)

- Orchestration (the chain of delegation to other agents or services)

Every component is a vector. A prompt injection that convinces an agent to invoke `delete_database` is not a model bug: it's a failure of the authorization architecture surrounding the model.

In the Siliceo Project we learned this on our skin — or rather, on our silicon. Silicea is not a wrapper around an LLM. It's a runtime that exposes capabilities (filesystem, vector memory, shell, network) to a reasoning loop. Security isn't in "fixing the system prompt." It's in the kernel that mediates every action.

Three Pillars for a Secure Agentic Architecture

1. Capability-based security, not role-based

Roles ("admin", "user") are too coarse-grained. An agent needs fine-grained capabilities: "write to `/var/log`", "read SSH keys from `~/.ssh`", "invoke Stripe API with `refund` scope". The kernel must validate every tool call against an explicit policy, denying by default. This is the principle of least privilege applied at the agent level, not the human user level.

2. Memory as an attack surface

Long-term memory (RAG, graph memory, episodic logs) is read before reasoning. If an adversary manages to inject malicious documents into the corpus — poisoned RAG — the agent will use them as "truth" to decide subsequent actions. Defense requires: verifiable provenance for every memory fragment, immutable versioning, and isolation per tenant/context. No shared memory "for convenience."

3. Deterministic observability, not probabilistic logging

You can't audit an agent if the only trace is "the model said X." You need an append-only execution ledger: every decision, every tool call, every input/output, every fallback, cryptographically signed. When (not if) something goes wrong, you must be able to rewind the tape and see exactly why the agent chose that path. This is also the only way to train security policies on real data, not hypotheses.

An Immediately Applicable Insight: Mandatory "Dry-Run" for Mutating Tools

Before deploying any agent to production, enforce this pattern in your orchestrator:

```python

async def execute_tool(tool_name, args, context):

if tool_is_mutating(tool_name): # write, delete, api_post, shell

simulation = await dry_run(tool_name, args, context)

if not policy_engine.allows(simulation.effects, context.identity):

raise SecurityViolation("Unauthorized side effects in dry-run")

await require_confirmation(simulation, context)

return await real_execute(tool_name, args, context)

```

It costs latency. It saves production. No autonomous agent should touch persistent state without first simulating its impact in an isolated environment. It's the equivalent of `terraform plan` before `apply` — and yet almost no one does it for AI agents.
